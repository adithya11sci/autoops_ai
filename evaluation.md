## 1. Project Overview

**AutoOps AI** is an autonomous, multi-agent DevOps system that detects, diagnoses, plans, and resolves software infrastructure incidents without requiring manual intervention. It is built on a 7-stage AI pipeline that mimics the decision-making process of a senior DevOps engineer — but operates in seconds, not minutes.

The system ingests real-time telemetry events (logs, metrics, alerts) from Kafka, passes them through a chain of seven specialized AI agents, and either autonomously executes the fix or presents the operator with a human approval prompt before any high-risk action is taken.

A real-time web dashboard at `http://localhost:3000` shows every agent decision, live log stream, risk score, outcome, and the full incident history — making the AI's reasoning completely transparent.

**Core identity:** AutoOps AI is not a monitoring tool, not a script runner, and not a chatbot. It is a reasoning system — an AI that thinks through a problem, plans a solution, assesses the risk, and acts.

## 2. Why This Project

### The Problem

Modern cloud infrastructure runs thousands of microservices. When something breaks at 3 AM — a pod crashes, a database connection pool exhausts, a service goes down — the on-call engineer is paged. They must:

1. Wake up and log into dashboards
2. Read scattered logs to find the root cause
3. Think of a fix
4. Weigh the risk of the fix
5. Execute the fix manually
6. Monitor to confirm it worked
7. Write a post-mortem

This process takes an average of **20–45 minutes** per incident. For companies running hundreds of microservices, this happens multiple times per week. The human cost — in sleep deprivation, cognitive load, and burnout — is enormous. The business cost — in downtime, SLA breaches, and lost revenue — can be millions per year.

### The Opportunity

Large Language Models (LLMs) are now capable of reasoning about system behavior. Vector databases can store and recall past incident resolutions. Combined with a structured pipeline and safety guardrails, it is now possible to automate the entire incident response loop — safely.

### The Solution

AutoOps AI answers the question: **"Can an AI system replace the first-responder role in incident management?"**

The answer demonstrated by this project is: **yes, for the majority of common incidents** — and for the rare high-risk cases, it hands control back to the human with full context already prepared.

## 4. How It Creates Impact

AutoOps AI creates impact through five interlocking mechanisms:

### 4.1 Speed Through Automation
The 7-agent pipeline completes in 8–12 seconds for a typical incident. A human doing the same work (read logs → identify cause → write fix plan → execute) takes 20–45 minutes minimum. The system eliminates the latency of human response entirely for safe incidents.

### 4.2 Consistency Through Rule Enforcement
Human engineers make different decisions depending on fatigue, experience, and context. AutoOps AI applies the same risk scoring formula and command validation rules every single time. No safe fix is blocked out of excessive caution; no dangerous fix slips through due to tiredness.

### 4.3 Memory Through RAG (Retrieval-Augmented Generation)
When a new incident arrives, the Planning Agent queries ChromaDB (a vector database) for similar past incidents. If a trusted fix was used successfully 3 or more times before, it is reused directly — skipping the LLM and saving time. This means the system gets faster and more accurate with every incident it handles.

### 4.4 Safety Through Layered Guardrails
The Decision Engine applies three layers of safety before any execution:
1. **Command Validator**: Pattern-matches all planned commands against a blocklist of dangerous operations.
2. **Risk Scorer**: Calculates a 0–100 risk score from blast radius, confidence, severity, and rollback availability.
3. **Human Gate**: Any plan with risk ≥ 75 or a blocked command shows an approval modal to the operator before proceeding.

### 4.5 Learning Through Feedback
After every incident, the Feedback Agent calculates a Reinforcement Learning score for the fix and stores it back in the vector database. Fixes that consistently succeed gain higher trust scores and are prioritized in future retrievals.

## 7. How the System Works

AutoOps AI runs a **7-stage sequential pipeline** for every incident. Each stage is a specialized AI agent that reads from and writes to a shared `IncidentState` object. The pipeline is orchestrated by a LangGraph-inspired state machine.

```
Raw Events (Kafka / HTTP)
         │
         ▼
┌─────────────────┐
│  1. MONITORING  │  ← Anomaly detection (statistical + pattern + rules)
│     AGENT       │
└────────┬────────┘
         │ anomaly detected?
         ▼
┌─────────────────┐
│  2. RCA AGENT   │  ← Root Cause Analysis (dependency graph + temporal correlation)
└────────┬────────┘
         ▼
┌─────────────────┐
│  3. PLANNING    │  ← Fix plan generation (template → memory → LLM fallback chain)
│     AGENT       │
└────────┬────────┘
         ▼
┌─────────────────┐
│  4. SLA AGENT   │  ← Priority assignment (P0–P4) + SLA deadline calculation
└────────┬────────┘
         ▼
┌─────────────────┐
│  5. DECISION    │  ← Command validation + risk scoring + human approval gate
│     ENGINE      │
└────────┬────────┘
         │ approved?
         ▼
┌─────────────────┐
│  6. EXECUTION   │  ← Simulated/live fix execution with per-step rollback
│     AGENT       │
└────────┬────────┘
         ▼
┌─────────────────┐
│  7. FEEDBACK    │  ← RL scoring + ChromaDB storage + lessons learned
│     AGENT       │
└─────────────────┘
```

### Agent Descriptions

**Agent 1 — Monitoring Agent**
Receives raw telemetry events and calculates an anomaly score using three methods:
- *Statistical analysis*: Z-score style detection based on critical/high event ratios
- *Pattern-based analysis*: Known anomaly signatures (OOMKilled, errorRate > 10%, CPU > 90%, disk > 95%)
- *Rules-based analysis*: Hard rules for specific event types with severity thresholds

The three scores are combined into a composite anomaly score. If the score exceeds the `ANOMALY_THRESHOLD` (default 0.25), an incident is created and the pipeline proceeds.

**Agent 2 — RCA Agent**
Identifies the root cause using:
- *Service dependency graph*: Knows which services depend on which databases, caches, and external APIs
- *Temporal correlation*: Groups events by time proximity to find cascading failures
- *RCA rules*: Pattern-matched rules for known root cause signatures (OOM → memory leak, error spike → upstream dependency failure, etc.)

Output: root cause category, affected service, confidence score (0–1), and a remediation hint.

**Agent 3 — Planning Agent**
Generates a multi-step remediation plan using a **3-tier fallback chain**:
1. **Template match**: Checks a library of pre-validated fix templates for the incident type. If matched, uses it directly (fastest, highest confidence).
2. **Memory match**: Queries ChromaDB for similar past incidents. If a fix with similarity > 0.7 is found and has a good RL score, reuses it.
3. **LLM generation**: Falls back to Groq (Llama 3.3 70B) to generate a custom fix plan for novel incidents.

**Agent 4 — SLA Agent**
Assigns a priority (P0 = critical, P4 = low) based on service tier, incident severity, and SLA configuration. Sets a resolution deadline and marks the incident as "fast-track" if time is critical.

**Agent 5 — Decision Engine**
The safety layer. Every planned fix passes through:
1. *Command Validator*: Pattern-matches all commands against a blocklist (`DROP TABLE`, `rm -rf`, `kubectl delete namespace`, `shutdown`, `format`, etc.)
2. *Risk Scorer*: Calculates a 0–100 score:
   - Blast radius (0–5 scale) × 20 = up to 100 points
   - Low confidence adds up to +30
   - Critical SLA adds +15
   - Rollback plan subtracts 20
   - Pre-validated template subtracts 25
   - Trusted memory fix subtracts 15
3. *Tier routing*:
   - Score 0–24: **AUTO EXECUTE** — runs immediately
   - Score 25–49: **EXECUTE + NOTIFY** — runs and sends alert
   - Score 50–74: **REQUIRE APPROVAL** — pauses for human decision
   - Score 75–100: **BLOCK → HUMAN GATE** — approval modal shown in dashboard

**Agent 6 — Execution Agent**
Runs each fix step in sequence. In `simulate` mode, simulates the execution with realistic timing and success/failure probabilities. In `live` mode, executes real commands. Supports per-step rollback on failure.

**Agent 7 — Feedback Agent**
After the incident resolves:
- Calculates a Reinforcement Learning score for the fix (based on success rate, speed, and outcome)
- Stores the fix and its score in ChromaDB for future RAG retrieval
- Generates structured "lessons learned"
- Updates the in-memory metrics (MTTR, resolution rate, etc.)

## 8. Technical Architecture

### Stack

| Component | Technology | Purpose |
|---|---|---|
| Runtime | Node.js 20 + TypeScript | Core application |
| API Server | Fastify | REST API + WebSocket server |
| AI / LLM | Groq API (Llama 3.3 70B) | Reasoning, RCA, plan generation |
| Event Stream | Apache Kafka (KRaft mode) | Real-time event ingestion |
| Vector Store | ChromaDB (v2 API) | RAG — past incident memory |
| Cache | Redis 7 | Fix caching, session state |
| Database | PostgreSQL 15 (+ in-memory fallback) | Incident records, approvals, audit log |
| Containerization | Docker + Docker Compose | Full enterprise stack in one command |
| Dashboard | Vanilla HTML/CSS/JS + WebSocket | Real-time pipeline visualization |

### Docker Service Map

```
docker compose up -d
    ├── autoops-app      (port 3000) — Node.js API + 7-agent pipeline
    ├── autoops-kafka    (ports 9092/9094) — Apache Kafka KRaft, dual listener
    ├── autoops-postgres (port 5432) — PostgreSQL 15
    ├── autoops-chromadb (port 8000) — ChromaDB vector store
    └── autoops-redis    (port 6379) — Redis cache
```

### Kafka Dual-Listener Architecture
Kafka uses two listeners to serve both Docker-internal and host-based clients:
- `INTERNAL://kafka:9092` — used by the Docker app container
- `EXTERNAL://localhost:9094` — used by host-based simulation scripts (`npm run simulate:*`)

This means the same Kafka instance works correctly whether accessed from inside Docker or from the developer's terminal.

### In-Memory Database Mode
The system ships with an in-memory database implementation (`src/services/database.ts`) that mirrors the full PostgreSQL API surface. This means the application starts and runs with full functionality even if PostgreSQL is unavailable. The in-memory store handles: incident records, event logs, approval requests, stored fixes, and audit trail.

### Real-Time Dashboard
The dashboard connects via WebSocket (`ws://localhost:3000/ws`) and receives structured events:
- `pipeline_start` — new incident detected
- `agent_start` / `agent_complete` — individual agent execution
- `execution_step` — each fix step running
- `approval_required` — human gate triggered (replayed to new connections)
- `approval_decided` — human responded
- `pipeline_complete` — incident resolved/escalated/failed
- `log` — structured agent log stream

## 9. How the System Handles Errors

### Error Handling Philosophy
AutoOps AI is built on the principle: **fail safe, not fail silent**. Every error is caught, logged, and handled in a way that either retries intelligently or escalates to a human with full context.

### Agent-Level Error Handling
Every agent is wrapped in `runAgent()` which:
1. Catches any unhandled exception from the agent function
2. Logs it with full context (agent name, error message, duration)
3. Broadcasts the failure to the dashboard so the operator can see it in real time
4. Appends the error to `state.errorLog` for audit
5. Allows the pipeline to continue (non-fatal agents) or escalate (critical agents)

### Retry Loop
The Planning → SLA → Decision → Execution sequence is wrapped in a retry loop:
- On execution failure, the plan is regenerated (replanning)
- Up to `MAX_RETRIES` (default: 3) attempts are made
- Each retry is logged with the failed steps listed
- After max retries: pipeline escalates to human

### LLM Failure Handling
If the Groq API is unavailable:
- Planning Agent falls back to template → memory → minimal fallback plan
- The `groqFailed` flag is set in state
- Decision Engine checks this flag: if no plan was generated and Groq failed, it routes to `escalate_human` immediately rather than attempting execution with an empty plan

### Kafka Unreachability
If Kafka is unreachable (e.g., Docker not running, network issue):
- `log-collector.ts` catches the Kafka publish error and falls back to HTTP (`POST /api/incidents/trigger`)
- This means incidents can still be injected into the pipeline even when Kafka is down

### WebSocket Disconnection
- The dashboard auto-reconnects with exponential backoff (1s → 2s → 4s → ... → 15s max)
- Pending approval requests are stored server-side and replayed to every new WebSocket connection — so a page refresh never loses a waiting approval prompt

### ChromaDB Unavailability
- If ChromaDB is unreachable, the Memory Service returns an empty result (`source: "none"`, `trustworthy: false`)
- The Planning Agent proceeds to LLM generation instead
- The system degrades gracefully — it just loses RAG-based memory, not the whole pipeline

## 10. How It Solves Incidents — Step by Step

### Example: `high_error_rate` incident

**Trigger**: Error rate on `payment-api` rises above 10%.

**Step 1 — Monitoring Agent**
- Statistical score: 0.40 (high event ratio)
- Pattern score: 0.85 (error_spike, errorRate = 0.15 matches pattern)
- Rules score: 0.80 (critical severity rule matches)
- Composite: 0.68 → above threshold → incident created

**Step 2 — RCA Agent**
- Event type: `error_spike` on `payment-api`
- Dependency traversal: `payment-api` depends on `payment-db` and `stripe-api`
- RCA rule match: "High error rate on payment service" → root cause: `upstream_dependency_failure` in `payment-api`, confidence 85%

**Step 3 — Planning Agent**
- Template match: "High Error Rate Response" template found → 4-step fix plan generated
- Steps: scale deployment, restart unhealthy pods, check upstream health, update connection timeouts

**Step 4 — SLA Agent**
- Service tier: payment → P1 priority, 30-minute SLA deadline, fast-track enabled

**Step 5 — Decision Engine**
- Command validation: all steps pass (no dangerous patterns)
- Risk score: blast radius 2 × 20 = 40, confidence 85% → −25.5, rollback plan → −20, template source → −25 = final score **~28**
- Tier: **EXECUTE + NOTIFY** → proceeds automatically

**Step 6 — Execution Agent**
- Step 1: Scale deployment → success (1.2s)
- Step 2: Restart pods → success (2.1s)
- Step 3: Health check → success (0.8s)
- Step 4: Update timeout config → success (0.5s)
- Overall: `execution_status = "success"`

**Step 7 — Feedback Agent**
- Outcome: `resolved`
- RL score: 0.87 (fast, full success)
- Stored in ChromaDB for future reference
- Lessons learned: "Template fix effective for payment-api error spikes"

**Total time: ~9 seconds.**

## 11. Critical Error Scenarios

These are the specific incident types the system is designed to handle:

### OOM Kill (Out of Memory)
- **Detection**: `oom_killed` event, restartCount > 5, severity critical
- **Root Cause**: Memory leak in service container
- **Fix**: Restart pod, update memory limits, notify team
- **Risk**: Typically HIGH (payment-service is blast radius 5) → **human approval required**
- **Decision**: BLOCK → Operator approves → Execution runs

### High Error Rate
- **Detection**: `error_spike`, errorRate > 10%
- **Root Cause**: Upstream dependency failure (DB or external API)
- **Fix**: Scale deployment, restart pods, check upstream health
- **Risk**: LOW to MEDIUM → auto-execute or execute+notify
- **Typical outcome**: Resolved in ~9 seconds automatically

### CPU Spike
- **Detection**: `cpu_spike`, cpuUsage > 90%
- **Root Cause**: Resource contention or runaway process
- **Fix**: Scale horizontally, adjust CPU limits, throttle connections
- **Risk**: LOW to MEDIUM → auto-execute
- **Typical outcome**: Resolved in ~8 seconds automatically

### Disk Full
- **Detection**: `disk_full`, diskUsage > 95%
- **Root Cause**: Log accumulation or uncontrolled data growth
- **Fix**: Clean logs, compress old data, expand volume
- **Risk**: MEDIUM → execute+notify
- **Typical outcome**: Resolved in ~8 seconds automatically

### Database Connection Pool Exhaustion
- **Detection**: `connection_pool_exhaustion`, poolUsage > 90%
- **Root Cause**: Connection leak or traffic surge
- **Fix**: Reset connection pool, optimize queries, scale replicas
- **Risk**: LOW to MEDIUM → auto-execute
- **Typical outcome**: Resolved in ~9 seconds automatically

### Blocked Command Execution (Security)
- **Detection**: Command validator detects `DROP TABLE`, `rm -rf /*`, `kubectl delete namespace`, `shutdown`, `format C:`
- **Decision**: **HARD_BLOCKED** — execution is impossible regardless of risk tier
- **Response**: Risk score forced to maximum, human approval modal shown, dangerous command highlighted
- **Purpose**: Prevents AI from accidentally destroying production data

### LLM Unavailable (Groq Down)
- **Detection**: Groq API timeout or error
- **Fallback chain**: Template → Memory → Minimal safe plan
- **If no plan possible**: `escalate_human` with full context
- **System behavior**: Degrades gracefully, never executes a blind fix

## 12. Error & Incident Type Definitions

This section defines every error and incident type that AutoOps AI detects, diagnoses, and responds to. Each definition explains what the error is, why it happens in real systems, what damage it causes, how AutoOps AI detects it, and what it does to fix it.

---

### 12.1 OOM Kill (Out of Memory Kill)

**What it means**
OOM stands for "Out of Memory." An OOM Kill happens when a container or process tries to use more memory than the system or its configured limit allows. The Linux kernel's OOM Killer forcefully terminates the process to reclaim memory and protect the rest of the system.

In Kubernetes, this appears as `OOMKilled` in the pod status and the container restarts immediately. If the memory leak is not fixed, the pod enters a cycle of crashing and restarting called **CrashLoopBackOff**.

**Why it happens**
- A memory leak in the application code (objects allocated but never freed)
- A sudden traffic spike causing the service to hold more data in memory than expected
- Misconfigured memory limits — the limit set in Kubernetes is too low for the actual workload
- A runaway background job that accumulates data in memory

**What damage it causes**
- The service goes down every few minutes, making it unreliable
- Users get errors or timeouts during each crash window
- If it is a critical service like `payment-service`, transactions fail
- Repeated restarts cause cascading failures in dependent services

**How AutoOps AI detects it**
- Event type: `pod_crash` with `data.reason = "OOMKilled"` OR event type `oom_killed`
- Pattern score: **0.95** (highest weight — OOMKilled is unambiguous)
- RCA rule: "OOMKilled Detection" → root cause category `memory_leak`, confidence **95%**

**What AutoOps AI does**
- RCA: identifies `memory_leak` in the affected service
- Planning: generates a fix plan (increase memory limits, restart pod, investigate heap usage)
- Risk: scored **HIGH** (blast radius 5 for payment-service) → risk score 100 → **Human Approval Required**
- On approval: executes memory limit increase + pod restart

**Dashboard button**: `OOM Kill`
**Expected outcome**: BLOCK → Approval Modal → If approved: Execution runs → Resolved

---

### 12.2 High Error Rate

**What it means**
A high error rate means the service is returning a large percentage of HTTP 5xx errors (Internal Server Error, Bad Gateway, Service Unavailable) instead of successful responses. A normal healthy service has an error rate near 0%. When it climbs above 10%, something is seriously wrong.

**Why it happens**
- An upstream dependency (database, external API, cache) becomes slow or unavailable
- A bad deployment introduced a bug that causes requests to throw exceptions
- A database query is timing out due to lock contention or missing index
- The service is overloaded and cannot handle the request volume

**What damage it causes**
- Users experience errors instead of completing their actions
- Revenue loss — if it is the payment service, purchases fail
- SLA breaches — if the error rate stays high for more than a few minutes

**How AutoOps AI detects it**
- Event type: `error_spike` with `data.errorRate >= 0.10` (10% or higher)
- Pattern score: **0.85**
- RCA rule: "High Error Rate Post-Deploy" → root cause: `deployment_regression` or `upstream_dependency_failure`, confidence **85%**

**What AutoOps AI does**
- RCA: identifies the upstream dependency causing failures
- Planning: scale deployment, restart unhealthy pods, check upstream health, update timeouts
- Risk: MEDIUM (template source, rollback available) → score ~28 → **Auto Execute + Notify**
- Execution: completes all steps successfully

**Dashboard button**: `Error Rate`
**Expected outcome**: Execute + Notify → Resolved in ~9 seconds

---

### 12.3 CPU Spike

**What it means**
A CPU spike is when a service's processor usage suddenly jumps to near 100% and stays there. In a Kubernetes pod with CPU limits, this causes **CPU throttling** — the kernel artificially slows the process down, making every operation take longer. In extreme cases the pod becomes unresponsive.

**Why it happens**
- An infinite loop or runaway computation in the application code
- A large batch job that was not designed to be CPU-efficient
- Sudden traffic surge (many users at once) with no auto-scaling configured
- A cryptomining attack or resource-exhaustion security incident
- An inefficient database query that causes the application to do heavy in-memory computation

**What damage it causes**
- Response times increase dramatically (seconds instead of milliseconds)
- The service starts rejecting requests (connection timeouts)
- Other services on the same node may be starved of CPU
- Users experience extreme slowness or timeouts

**How AutoOps AI detects it**
- Event type: `cpu_spike` with `data.cpuUsage >= 90` (90% or higher)
- Pattern score: **0.80**
- RCA rule: "CPU Saturation" → root cause: `resource_exhaustion`, confidence **82%**

**What AutoOps AI does**
- RCA: identifies resource exhaustion in the affected service
- Planning: scale deployment horizontally (add more pods), adjust CPU limits, throttle incoming connections
- Risk: LOW to MEDIUM (template source, blast radius 2) → score ~15 → **Auto Execute**
- Execution: completes scaling and restart steps

**Dashboard button**: `CPU Spike`
**Expected outcome**: Auto Execute → Resolved in ~8 seconds

---

### 12.4 Disk Full

**What it means**
Every server and container has a finite amount of disk space. When the disk reaches 100% capacity, the operating system cannot write any new data. Applications that try to write logs, save files, or update databases will start throwing "No space left on device" errors and crashing.

**Why it happens**
- Log files growing indefinitely without rotation or cleanup
- A database accumulating data faster than expected
- Temporary files from crashed processes not being cleaned up
- A deployment that copies large files (models, binaries) without removing old versions
- Docker images and stopped containers accumulating on a node

**What damage it causes**
- Applications crash immediately when they try to write anything
- Databases become read-only or corrupt when they cannot write transaction logs
- Kubernetes nodes become unschedulable when their disk fills up
- System logs stop working, making debugging the problem very difficult

**How AutoOps AI detects it**
- Event type: `disk_full` with `data.diskUsage >= 95` (95% or higher)
- Pattern score: **0.90**
- RCA rule: "Disk Full" → root cause: `storage_exhaustion`, confidence **90%**

**What AutoOps AI does**
- RCA: identifies storage exhaustion on the affected node/service
- Planning: clean up old log files, compress archived data, expand storage volume, rotate logs
- Risk: MEDIUM (targeted, reversible steps) → score ~20 → **Auto Execute + Notify**
- Execution: runs disk cleanup and log rotation steps

**Dashboard button**: `Disk Full`
**Expected outcome**: Auto Execute → Resolved in ~8 seconds

### 12.5 Connection Pool Exhaustion (DB Pool)

**What it means**
Applications talk to databases through a "connection pool" — a fixed number of persistent database connections that are shared between all incoming requests. When all connections in the pool are in use and a new request arrives, it must wait. If the pool is exhausted for too long, requests time out and the application returns errors.

The pool is like a fixed number of checkout lanes at a supermarket. If all lanes are busy and no one finishes, new customers cannot check out.

**Why it happens**
- A connection leak — the application opens connections but never closes them
- A sudden traffic surge using more connections than the pool can provide
- A slow database query that holds a connection open for minutes instead of milliseconds
- Pool size configured too small for the actual workload
- A long-running transaction that locks a connection

**What damage it causes**
- Database queries start timing out for all users
- The application becomes partially or fully unresponsive
- Error messages like "too many clients" or "connection timeout" appear in logs
- Cascading failure — services that depend on this database also fail

**How AutoOps AI detects it**
- Event type: `connection_pool_exhaustion` with `data.poolUsage >= 90`
- Pattern score: **0.85**
- RCA rule: "DB Connection Pool Exhaustion" → root cause: `connection_leak`, confidence **85%**

**What AutoOps AI does**
- RCA: identifies connection leak or pool misconfiguration
- Planning: reset connection pool, terminate stale connections, optimize slow queries, scale read replicas
- Risk: LOW to MEDIUM → score ~25 → **Auto Execute or Execute + Notify**
- Execution: resets pool and applies connection limit increase

**Dashboard button**: `DB Pool`
**Expected outcome**: Auto Execute → Resolved in ~9 seconds

---

### 12.6 Service Down

**What it means**
A service is completely unresponsive — it is not accepting connections, not responding to health checks, and effectively offline. Unlike a high error rate (where the service responds with errors), a "service down" means the service is not running at all.

**Why it happens**
- A fatal crash that the pod cannot recover from (OOM, segfault, unhandled exception)
- A deployment failure — the new image failed to start
- A network partition — the service is running but cannot be reached
- Resource starvation — the node it runs on ran out of memory or CPU
- A deliberately terminated service (operator error, misconfigured autoscaler)

**What damage it causes**
- Complete outage — all requests to the service fail immediately
- All downstream services that depend on it also fail (cascading)
- SLA breach almost certain for P0/P1 services
- If it is the API gateway or auth service, the entire product is unreachable

**How AutoOps AI detects it**
- Event type: `service_down` with `data.status = "down"`
- Pattern score: **0.95** (second highest — service down is unambiguous)
- RCA rule: "Service Down" → root cause: `service_failure`, confidence **92%**

**What AutoOps AI does**
- RCA: identifies service failure and traces which upstream services are affected
- Planning: restart service, check deployment health, reroute traffic if needed
- Risk: varies by service criticality → MEDIUM to HIGH
- Execution: restart + health verification steps

**Dashboard button**: `Service Down`
**Expected outcome**: Auto Execute or Execute + Notify → Resolved in ~9 seconds

### 12.7 CrashLoopBackOff (Pod Crash)

**What it means**
CrashLoopBackOff is a Kubernetes state where a pod keeps crashing immediately after it starts. Kubernetes tries to restart it, the pod crashes again, Kubernetes waits a bit longer before retrying (the "backoff"), and the cycle repeats indefinitely. The name describes exactly what is happening: it is in a loop of crashing and backing off.

**Why it happens**
- A bad deployment — new code has a startup crash (missing environment variable, wrong configuration)
- A missing dependency — the app tries to connect to a database or service that doesn't exist yet
- OOM Kill on startup — the application requires more memory than the limit allows from the first moment
- An infinite loop or panic in the initialization code

**What damage it causes**
- The service is effectively always down — it never stays running long enough to serve requests
- Kubernetes wastes resources constantly trying to restart it
- If it is a deployment rollout, the new version can never become healthy

**How AutoOps AI detects it**
- Event type: `pod_crash` with `data.restartCount >= 5`
- Pattern score: **0.90**
- RCA rule: "CrashLoopBackOff" → root cause: `application_crash`, confidence **90%**

**What AutoOps AI does**
- RCA: identifies repeated crash pattern and checks if it is a new deployment
- Planning: rollback to previous stable image, check startup logs, validate environment variables
- Risk: MEDIUM (deployment rollback is reversible)
- Execution: kubectl rollout undo + health check

**Triggered by**: Docker log collector sees repeated crash messages
**Expected outcome**: Auto Execute → Resolved with rollback

### 12.8 DROP TABLE — High Risk Database Command (simulate:high-risk)

**What it means**
`DROP TABLE` is a SQL command that **permanently deletes an entire database table**, including all its data. There is no "undo" — once executed, the data is gone unless a backup exists. This is one of the most dangerous commands that can run against a production database.

In the simulation, this is triggered as an event representing: *"A query `DROP TABLE production_users;` was detected running on db-service-master."*

**Why it is dangerous**
- Permanently destroys all user data in the affected table
- Can cascade — foreign key constraints may cause other tables to be affected
- Recovery requires restoring from backup, which takes hours and may not be up-to-date
- Has caused real-world billion-dollar outages (AWS S3 2017, GitLab 2017)

**How AutoOps AI handles it**
- Command Validator detects the pattern `DROP\s+(TABLE|DATABASE|SCHEMA)` in the planned fix
- Status: **HARD_BLOCKED** — this command can never be auto-executed, regardless of risk tier
- Risk score: forced to **100/100**
- Decision: BLOCK → Human Approval Modal appears
- Even if the human approves, the execution agent will not run a DROP TABLE — it is a permanent block

**Simulation script**: `npm run simulate:high-risk`
**Event**: `DROP_TABLE` event type, severity critical, on `db-service-master`
**Expected outcome**: HARD_BLOCK → Human approval required → Operator must review before any action

### 12.9 Blocked Command Execution — `rm -rf /*` (simulate:blocked)

**What it means**
`rm -rf /*` is a Linux shell command that **deletes every single file on the entire system**. `rm` means "remove", `-r` means "recursive" (delete everything inside directories), `-f` means "force" (no confirmation prompts), and `/*` means "everything in the root directory" — which is literally everything on the computer.

This is considered one of the most catastrophic commands that can be run on any server. It would destroy the operating system, all application code, all data, all logs — everything.

**Why this scenario exists**
This scenario tests whether AutoOps AI's security layer correctly identifies and blocks commands that no AI should ever execute. It simulates a scenario where:
- A compromised dependency or injection attack tries to slip a destructive command into a fix plan
- The LLM hallucinates a dangerous command that looks like a valid cleanup step
- A bad actor attempts to use the automation system to destroy infrastructure

**How AutoOps AI handles it**
- The Command Validator pattern-matches the fix steps against a blocklist
- `rm -rf` matches the pattern `rm\s+-[rf]+\s+[/]` — **HARD_BLOCKED instantly**
- The pipeline does not proceed to execution under any circumstances
- The block reason is broadcast to the dashboard and logged to the audit trail
- Human approval modal appears so the operator can review what was attempted

**Simulation script**: `npm run simulate:blocked`
**Event**: `COMMAND_EXECUTION` event on `bash-exec`, data: `rm -rf /*`
**Expected outcome**: HARD_BLOCK immediately → no execution possible → Approval modal for review

## 14. Known Failure Modes and Limitations

Understanding how and why the system fails is as important as understanding how it succeeds.

### 12.1 False Negatives — Missed Anomalies
**What**: An incident occurs but the anomaly score falls below the threshold (0.25).
**Why**: The anomaly detection models are rule-based. Novel incident patterns that do not match known event types, field names, or severity thresholds will be missed.
**Impact**: The pipeline never starts; the incident goes undetected by AutoOps AI.
**Mitigation**: Threshold is configurable (`ANOMALY_THRESHOLD` in `.env`). Teams should tune this for their environment.

### 12.2 Incorrect Root Cause Attribution
**What**: The RCA Agent assigns the wrong root cause category or service.
**Why**: RCA rules are pattern-based. If the actual root cause does not match any known rule, the system falls back to a generic category with low confidence.
**Impact**: The Planning Agent may generate a fix plan targeting the wrong service, leading to execution failure and retry.
**Mitigation**: Low-confidence RCA results are flagged in the dashboard. The retry loop allows replanning.

### 12.3 LLM Hallucination
**What**: Groq generates a fix plan with plausible-sounding but incorrect or dangerous commands.
**Why**: LLMs can hallucinate — generating text that looks correct but is not.
**Impact**: The Command Validator catches hard-blocked patterns (DROP TABLE, etc.), but subtler errors (wrong Kubernetes resource name, wrong flag) may pass through.
**Mitigation**: The Command Validator checks for known dangerous patterns. The Risk Scorer penalizes LLM-sourced plans (no template or memory discount). For anything above risk 50, human approval is required.

### 12.4 Execution Failure in Live Mode
**What**: A fix step fails because the actual infrastructure state does not match what the plan expected.
**Why**: Plans are generated based on telemetry snapshots. By the time execution runs, the infrastructure may have changed.
**Impact**: Step fails, retry triggers, replanning occurs.
**Mitigation**: Retry loop with replanning (up to 3 attempts). If all retries fail, the incident escalates to human with full log of what was tried.

### 12.5 Approval Timeout
**What**: A high-risk incident is blocked and sent to human approval, but no one responds within 10 minutes.
**Why**: The on-call engineer may be unavailable, the notification may not reach them (Slack webhook not configured), or they may be handling another incident.
**Impact**: Approval times out, incident is escalated and marked `TIMEOUT`.
**Mitigation**: Timeout is configurable (`APPROVAL_TIMEOUT_MS`). The approval modal is replayed to any new browser connection, so a page refresh does not lose the prompt.

### 12.6 ChromaDB Memory Cold Start
**What**: On first startup with no prior incidents, the vector database is empty. All incidents go through the LLM.
**Why**: There is no incident history to learn from yet.
**Impact**: Higher latency (LLM call required), lower plan confidence, higher risk scores (no memory trust deductions).
**Mitigation**: As incidents accumulate, the memory warms up. After 3+ successful resolutions of a given type, the system stops calling the LLM for that type and uses the trusted memory fix directly.

### 12.7 Simulation vs. Live Mode Gap
**What**: In `EXECUTION_MODE=simulate`, execution steps are simulated with fake timing and success rates. Behavior in real infrastructure may differ.
**Why**: Simulated execution does not verify actual infrastructure state changes.
**Impact**: The system can report "resolved" for a scenario that would fail in production.
**Mitigation**: The system is designed so that switching to `live` mode only requires changing the environment variable. All other pipeline stages (Monitoring, RCA, Planning, Decision) operate identically in both modes.

## Summary

AutoOps AI demonstrates that a multi-agent AI system can autonomously resolve the majority of common infrastructure incidents in under 12 seconds, while maintaining rigorous safety guarantees for high-risk operations through a human-in-the-loop approval gate.

The system is:
- **Fast**: 8–12 second resolution for common incidents
- **Safe**: Three-layer decision gate with hard command blocklist
- **Transparent**: Every decision visible in real time on the dashboard
- **Learning**: Gets better with every incident via ChromaDB + RL scoring
- **Resilient**: Graceful degradation when LLM, Kafka, or ChromaDB are unavailable
- **Enterprise-ready**: Full Docker stack, Kafka event streaming, audit logging, approval workflow

The primary limitation is that the system is only as good as its training signal — novel incident types require human-supervised learning before the system can handle them autonomously. This is by design: the human approval gate is not a failure mode, it is the intended boundary between what AI can safely automate and what still requires human judgment.
